# 내가 만든 프로젝트를 제대로 이해하기

**사용자가 전체 정리나 복습을 요청했을 때만** 사용한다. 평소 구현을 느리게 만드는 필수 절차가 아니다.

## 먼저 확인할 것

- 현재 요청, `SPEC.md`(있다면), 최신 코드, 실제 실행 결과·검사 기록, 결과 문서를 살핀다. 작업 대화나 결정 기록이 접근 가능하면 필요한 부분만 참고한다.
- **지금 구현된 것**을 기준으로 쓴다. 이전 계획, 실제로 검증한 내용, 아직 확인하지 못한 내용은 섞지 않는다.
- 자료가 없어 확인할 수 없는 부분은 `확인 못 함`이라고 적는다. 없던 대화·설계 이유·검사·실패 경험을 지어내지 않는다.
- 자료를 전부 복사해 붙이지 말고, 결과를 이해하는 데 필요한 코드와 사례를 고른다.

## 만들어 줄 문서

별도 파일명이 지정되지 않았다면 작업 프로젝트에 `PROJECT_WALKTHROUGH.md`로 작성한다. 아래 여섯 주제를 **쉽고 자연스러운 한국어**로 설명한다. 문서의 길이는 프로젝트의 크기와 사용자에게 남은 시간에 맞춘다.

### 1. 프로젝트 전체 그림
- 누구의 어떤 문제를 해결하는지, 최종 결과가 무엇인지 **먼저 세 문장 이내로** 알려준다.
- 입력 → 중요한 처리 단계 → 출력의 흐름을 보여준다. 핵심 파일은 그 흐름에서 하는 일과 함께 소개한다.

### 2. 핵심 동작을 실제 예시로 따라가기
- 중요한 업무 규칙과 계산을 **작은 실제 입력 하나**로 차근차근 설명한다.
- 어떤 값이나 기록이 선택·제외되고, 어떤 코드를 거쳐, 어떤 결과가 나오는지 연결한다. 예시와 실제 구현이 일치하는지 확인한다.

### 3. 왜 이렇게 만들었는지
- 실제로 선택한 언어·구조·처리 방식 중 중요한 것과 당시 이유를 설명한다.
- 도움이 되면 다른 방법과의 차이를 설명하되, **실제로 검토하지 않은 대안을 과거에 논의한 것처럼 말하지 않는다.**

### 4. 어디까지 확인했는지
- 중요한 검사에 대해 **입력 / 기대한 결과 / 실제 확인한 결과**를 나란히 설명하고, 근거가 되는 파일이나 실행 기록을 알려준다.
- 그 검사로 확인된 것과 **여전히 확인되지 않은 것**을 분명하게 나눈다. 실행한 적 없는 검사는 통과했다고 쓰지 않는다.

### 5. 어디서 깨질 수 있고, 바뀌면 어떻게 되는지
- 실제로 처리하는 오류, 예상 가능한 실패, 재실행할 때 남는 결과를 구분한다. 가능성만 있는 문제는 재현한 것처럼 쓰지 않는다.
- 중요한 입력이나 요구가 달라지면 어떤 코드와 출력이 영향받고 무엇을 다시 확인해야 하는지 작은 예로 설명한다.

### 6. AI와 어떻게 함께 만들었는지
- 확인 가능한 대화·작업 기록을 바탕으로, **사용자가 정한 목표와 중요한 선택**, **AI에게 맡긴 일**, **검토 후 바꾼 방향**을 구분한다.
- 결정 당시의 근거를 짚는다. 기록이 없으면 나중에 추정한 이유를 실제 대화처럼 꾸미지 않는다.

## 설명하는 방식과 학습 확인

- 이해에 중요한 낯선 개념은 **무슨 뜻인지 → 왜 필요한지 → 쉬운 예시** 순으로 풀어준다. 이해에 필요 없는 클래스명·약어·로그는 줄인다.
- 긴 요약보다 **실제 입력이 어떻게 출력으로 바뀌는지**, **검증 결과를 왜 믿을 수 있고 어디까지 믿어야 하는지**를 우선한다.
- 문서 마지막에 사용자가 스스로 점검해 볼 **핵심 질문 3~6개**를 넣는다. 정답을 바로 붙이지 않고, 질문마다 실제 코드나 기록에서 확인할 부분을 정한다.
- 사용자가 원하면 질문을 **한 번에 하나씩** 내고 답을 기다린다. 답변을 실제 코드·결과와 대조해 쉽게 설명한다. 사용자가 충분히 이해했다면 반복하지 않는다.
- 시간이 부족하다고 하면 여섯 주제를 한 페이지 안팎으로 압축한다. 필수 개발·검증·결과 전달을 밀어내면서 긴 문서나 연습을 강요하지 않는다.
