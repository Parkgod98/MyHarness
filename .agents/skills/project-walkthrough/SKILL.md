# 프로젝트 전체를 쉽게 이해하기

사용자가 요청할 때만 실행한다. 목적은 **처음 읽는 사람도 짧은 시간에 서비스의 전체 흐름을 머릿속에 그리도록 돕는 것**이다. 기술 보고서처럼 지식을 나열하지 않는다.

## 확인할 자료와 범위

- 현재 코드와 진입점, SPEC·요구사항, 실행·검증 기록을 실제로 읽는다. 대화·결정 기록이 있으면 필요한 만큼 확인한다.
- 지금 구현된 동작, 당시 선택 이유, 실제 검증 결과, 가능성·미검증을 구분한다. 확인 못 한 이유나 실패·사용자 결정을 지어내지 않는다.
- 별도 지시가 없다면 프로젝트의 \`PROJECT_WALKTHROUGH.md\` 하나만 작성한다. 다른 코드·기존 문서·테스트·제출물은 수정하지 않는다. 새 테스트를 무조건 실행하거나 장문의 증거를 복사하지 않는다.

## 문서 작성 순서

**처음 5~10분에 읽을 핵심 내용부터** 배치한다. 아래 여섯 관점은 빠뜨리지 않되 분량을 똑같이 할당하지 않는다.

1. **한눈에 보는 전체 그림:** 누구의 무슨 문제를 해결하는지 세 문장 이내. 이용자 흐름과 핵심 구성요소의 역할을 쉬운 말로 설명한다. 파일명 목록부터 시작하지 않는다.
2. **실제 입력 하나를 끝까지 따라가기:** 사용자의 행동 → 입력 → 계산·판단 → 저장·상태 변화 → 화면·출력 결과를 작은 값으로 보여준다. 각 단계에서 왜 그 결과가 나오는지도 설명한다.
3. **중요한 선택과 포기한 것:** 알고리즘·저장·구조의 핵심 선택, 선택 이유와 현실적인 대안을 설명한다. 실제 합의 기록이 없으면 현재 코드로 알 수 있는 장단점만 이야기한다.
4. **검증한 것과 못 한 것:** 중요한 시나리오별로 넣은 입력 → 기대한 결과 → 실제 확인한 결과를 보여준다. 기존 로그를 읽은 것과 이번에 직접 실행한 것은 명확히 구분한다.
5. **실패와 변경의 영향:** 오류·중복·동시 요청·재시작 등 실제 관련 있는 위험만 골라 '어떤 상황 → 실제 동작 → 남는 데이터'로 설명한다. 미재현 위험은 미재현이라고 쓴다.
6. **AI와 나의 역할:** 확인 가능한 원문을 바탕으로 사용자의 결정, AI가 구현한 부분, 실제 변경·거절 사례를 구분한다. 없던 논의를 만들지 않는다.

## 사람이 이해하는 설명 방법

- **설명 문장은 Codex의 기술 보고서체가 아니라, ChatGPT 6.1 Sol High Chat 모드에서 옆 사람에게 직접 알려주듯 자연스러운 한국어로 쓴다.** 이 지침은 머리말뿐 아니라 실제 본문 전체에 적용한다.
- 함수명·전문용어부터 설명하거나 '~을 수행한다', '~를 보장한다' 같은 문장을 이어 쓰지 않는다. 먼저 '이 상황에서는 어떻게 될까요? 이렇게 돼요. 이유는...'처럼 핵심 결과와 이유를 친근한 해요체로 풀어주고, 실제 코드·검증 근거는 뒤에 짧게 연결한다.
- **문서의 여섯 관점과 전체 설명 순서는 그대로 둔다.** 기술적 사실·검증의 불확실성·사용자와 AI의 판단 근거는 줄이거나 바꾸지 않는다. 말투만 바꾼다고 장황한 비유나 잡담을 늘리지 않는다.

- **먼저 상황과 궁금증 → 무슨 일이 일어나는지 → 왜 그렇게 되는지 → 실제 코드·검증 근거** 순서로 설명한다. 기술 용어·함수명·코드 위치로 문장을 시작하지 않는다.
- 개발자에게 말하듯 자연스러운 한국어를 쓴다. 생소한 용어는 첫 등장에 쉬운 뜻을 붙이고, 필요 없는 약어·추상적인 문구·긴 코드 인용은 줄인다.
- 표·흐름도는 이해가 더 쉬워질 때만 쓴다. 같은 내용을 그림·표·본문에 세 번 반복하지 않는다. 경로·줄 번호·로그 링크는 해당 설명의 끝이나 작은 근거 묶음에 둔다.
- **설명 예시(문체만 참고하며 예시 업무를 다른 프로젝트에 강요하지 않는다):**
  - 읽기 어려움: "예약 처리 시 멱등성을 확보하여 요청 재전송에 대한 상태 일관성을 보장한다."
  - 읽기 쉬움: "**예약 버튼을 두 번 누르면 예약도 두 개 생길까?** 서버가 같은 요청 번호인지 먼저 확인해. 이미 예약을 만들었다면 새로 만들지 않고 기존 결과를 보여줘. 그래서 응답이 끊겨 다시 보내도 중복 예약을 피할 수 있어. 실제 구현 위치와 이 동작을 검증한 기록은 아래에서 확인할 수 있어." 
- 예시가 실제 코드·검사에 맞지 않으면 사용하지 않는다. 증거가 없는 효과는 검증된 것처럼 쓰지 않는다.

## 완성 기준

- 처음 읽는 사람이 핵심 흐름 하나와 가장 중요한 선택·실패·검증 범위를 스스로 설명할 수 있게 작성한다.
- 전체 설명을 우선하고 구현 세부사항의 반복은 \`implementation-insight\`에 맡긴다. 짧아도 중요한 내용을 빼지 말고, 중요하지 않은 내용으로 읽는 시간을 늘리지 않는다.
- 끝에 스스로 답해 볼 핵심 질문 3~6개만 두고 정답이나 강제 승인 절차는 붙이지 않는다. 사용자가 요청하면 한 문제씩 쉽게 풀어 설명한다.
