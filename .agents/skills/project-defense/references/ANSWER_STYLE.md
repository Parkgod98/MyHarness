# 이해하기 쉬운 통합 질문과 답변 예시

이 문서는 `project-defense` Skill이 작성해야 할 **완성형 모범답안의 설명 방식**을 보여준다.

아래는 가상의 공동 비품 지원 서비스를 예시로 재구성한 내용이다. 다른 프로젝트에서 같은 기능, 알고리즘, 파일 구조, 질문 개수, 숫자를 사용하라는 의미가 아니다.

**핵심은 처음 읽는 사람도 답변만으로 동작과 판단 이유를 이해할 수 있게 설명하는 것이다.**

---

## 예시 1. 핵심 알고리즘과 선택 이유

### 질문

재고가 7개 남아 있습니다.

긴급 신청 A는 2개, 긴급 신청 B는 8개, 일반 신청 C는 4개가 더 필요합니다.

현재는 같은 우선순위의 신청에 물품을 하나씩 돌아가며 배분하는 방식을 사용합니다.

각 신청은 몇 개씩 지원받으며, 왜 이런 방식을 선택했을까요? 한 신청부터 전부 채우는 방식과 비교했을 때 한계는 무엇일까요?

### 모범답안

현재 방식대로라면 A에게 2개, B에게 5개, C에게 0개를 추가 지원합니다.

먼저 긴급 신청부터 처리하기 때문에 A와 B가 이번 배분 대상이 됩니다. 두 신청에 하나씩 나눠주다가 A가 필요한 2개를 모두 받으면, 그다음부터는 B에게만 남은 재고를 배분합니다. 결국 재고 7개를 긴급 신청에 모두 사용하므로 일반 신청 C는 이번에 지원받지 못합니다.

이 방식을 선택한 이유는 **같은 우선순위의 신청들에 이번 지원량을 최대한 고르게 나누기 위해서**입니다.

예를 들어 두 신청이 각각 10개와 20개를 필요로 하는데 재고가 6개뿐이라면 현재 방식은 3개씩 지원합니다. 반대로 첫 번째 신청부터 채운다면 6개와 0개가 됩니다.

첫 번째 신청을 빨리 완료하는 데는 한 신청부터 채우는 방식이 유리할 수 있습니다. 하지만 뒤의 신청은 한 개도 받지 못할 수 있죠.

현재 방식에도 한계가 있습니다. 긴급 신청이 계속 늘어나면 일반 신청이 장기간 기다릴 수 있고, 마지막 남는 수량에서는 신청 번호가 작은 쪽이 유리합니다. 또 여러 신청에 조금씩 지원하기 때문에 특정 신청을 빨리 완료하기는 어려울 수 있습니다.

즉, **이번 지원량의 균등함을 우선하는 대신, 신청별 빠른 완료와 일반 신청의 대기 시간 보장은 포기한 방식**입니다.

**핵심 한 문장:** 계산 결과뿐 아니라 어떤 공정성을 선택했고 무엇을 포기했는지 이해해야 합니다.

## 예시 2. 사용자 행동부터 DB 저장까지의 전체 흐름

### 질문

관리자가 배분 미리보기에서 총 6개를 지원할 수 있다는 결과를 확인했습니다. 다른 변경 없이 확정 버튼을 누릅니다.

화면에서 어떤 정보를 보내고, 서버는 무엇을 확인하며, 저장 후 결과가 화면에 어떻게 표시되는지 설명해 주세요.

### 모범답안

관리자가 확정 버튼을 누르면 브라우저는 선택한 배분 정책, 미리보기를 확인했을 당시의 자료 버전, 이번 확정을 구분하는 처리 식별자를 서버에 보냅니다. 로그인한 관리자임을 확인할 수 있는 인증 정보도 함께 전달합니다.

여기서 중요한 점이 있습니다. **브라우저가 각 신청에 몇 개씩 주라고 최종 수량을 결정해서 보내는 것은 아닙니다.**

서버는 먼저 관리자 권한을 확인합니다. 이후 이미 성공한 동일 요청인지 살펴보고, 새로운 요청이라면 관리자가 확인했던 버전과 현재 DB 버전이 같은지 검사합니다.

버전이 같으면 서버가 현재 재고와 배분 대상 신청을 DB에서 다시 읽습니다. 신청별 승인 상태, 우선순위, 아직 지원받지 못한 수량을 확인하고 정해진 배분 알고리즘을 적용합니다.

계산이 끝나면 신청별 누적 지원량과 상태를 갱신하고 재고를 차감합니다. 이때 자료 버전, 변경 이력, 이번 요청이 성공했다는 기록도 함께 저장합니다.

이 저장들은 하나의 트랜잭션으로 처리합니다. 여러 항목을 저장하는 도중 오류가 발생하면 일부만 반영되는 것이 아니라 전체 변경이 취소됩니다.

정상적으로 저장되면 서버는 배분 결과를 반환합니다. 그다음 브라우저가 최신 현황과 이력을 다시 조회해서 변경된 재고, 지원량, 신청 상태를 화면에 보여줍니다.

따라서 전체 흐름을 한마디로 정리하면 **화면은 확정 의사를 전달하고, 서버가 현재 자료를 검증하고 다시 계산한 뒤, 관련 내용을 안전하게 저장하고, 화면은 최신 결과를 다시 조회하는 것**입니다.

**핵심 한 문장:** 화면의 예상 결과를 그대로 믿고 저장하는 게 아니라 서버에서 다시 확인하고 계산합니다.

## 예시 3. 서버 재시작과 중복 요청, 자료 버전

### 질문

버전 7에서 보낸 배분 확정이 서버에서는 성공해 버전 8이 됐지만, 응답은 브라우저에 도착하지 않았습니다.

그사이 다른 입고로 버전 9가 됐고 서버도 재시작했습니다.

다시 로그인한 관리자가 다음 두 요청을 보내면 어떻게 될까요?

- 처음과 같은 처리 식별자, 같은 내용, 버전 7로 재전송
- 처리 식별자만 새것으로 바꾸고, 나머지는 버전 7 그대로 전송

각각의 처리 결과와 기존 재고, 이력에 미치는 영향을 설명해 주세요.

### 모범답안

두 요청은 서로 다르게 처리되지만, **어느 경우에도 재고나 이력이 추가로 변경되지는 않습니다.**

먼저 처음과 같은 처리 식별자와 같은 내용을 다시 보내면 서버는 예전에 성공한 요청이라는 사실을 발견합니다.

이 요청은 새로운 배분을 하려는 게 아니라 이미 끝난 배분이 성공했는지 확인하는 것이므로, 서버는 처음 저장했던 성공 결과를 HTTP 200으로 다시 반환합니다.

여기서 현재 버전이 9로 바뀌었다는 사실은 문제가 되지 않습니다. 이미 성공한 요청인지 먼저 확인하기 때문입니다.

성공한 요청 기록은 DB에 저장돼 있어서 서버를 재시작해도 유지됩니다. 로그인은 다시 해야 할 수 있지만, 같은 관리자 계정으로 원래 식별자를 사용하면 과거 결과를 확인할 수 있습니다.

반면 처리 식별자만 새로운 것으로 바꾸면 상황이 달라집니다.

서버는 처음 보는 식별자이므로 새로운 배분 요청이라고 판단합니다. 새로운 요청에는 현재 자료의 버전 검사가 적용됩니다.

그런데 요청에는 버전 7이 들어 있고 실제 DB 버전은 9입니다. 오래된 자료를 기준으로 확정하려는 것이므로 HTTP 409로 거절합니다.

이때도 실제 배분이 일어나지 않으므로 재고와 지원량, 이력은 그대로 유지됩니다.

두 개념을 구분하면 이해하기 쉽습니다.

**처리 식별자는 '전에 하던 그 작업인가?'를 구분하고, 자료 버전은 '현재 자료를 보고 새로운 작업을 하려는가?'를 확인합니다.**

따라서 같은 작업을 다시 확인하는 경우와 오래된 정보로 새로운 작업을 만드는 경우는 다르게 처리됩니다.

**핵심 한 문장:** 기존 성공 요청은 먼저 재확인하고, 새로운 요청에만 현재 버전을 검사합니다.

## 예시 4. AI와의 협업에서 사용자가 내린 판단

### 질문

개발 과정에서 사용자가 이미 확인한 환경 검사의 반복을 줄이고, 새로 구현한 기능의 핵심 검증에 집중하자고 제안했습니다.

왜 이런 판단을 했으며, 무엇을 줄이고 무엇을 유지했을까요? 그렇게 했을 때 생기는 위험은 무엇인가요?

### 모범답안

처음에는 기능을 하나 구현할 때마다 관련 테스트뿐 아니라 이전 기능과 실행환경까지 반복해서 확인했습니다.

그런데 개발환경 문제를 해결하는 데 예상보다 시간이 많이 들어갔고, 이미 확인한 항목을 반복해서 검증하는 데도 상당한 시간이 사용됐습니다.

그래서 모든 검증을 같은 빈도로 반복하기보다, **새로 만든 기능의 핵심 검사는 유지하면서 이전에 확인한 환경 설정과 무관한 반복 검사는 줄이자고 판단했습니다.**

예를 들어 새로운 신청 기능을 만들었다면 실제 신청이 저장되는지, 잘못된 수량이 거절되는지, 같은 요청을 재전송해도 중복 신청이 생기지 않는지는 반드시 검사해야 합니다.

반면 코드와 의존성이 달라지지 않았는데 이미 확인한 패키지 설치나 기본 실행환경을 처음부터 반복 점검하는 것은 우선순위가 상대적으로 낮다고 봤습니다.

다만 이렇게 하면 위험도 있습니다. 새 기능을 추가하면서 이전 기능이 고장 났더라도 전체 회귀 검증을 뒤로 미루면 문제를 늦게 발견할 수 있습니다.

그래서 변경한 기능과 직접 관련된 검사는 해당 단계에서 유지하고, 마지막에는 여러 기능을 연결한 전체 흐름을 다시 확인하는 방식으로 조정했습니다.

다음 개발 단계로 넘어갈 때는 해당 단계에서 구현하기로 한 기능이 완성됐는지, 주요 정상, 오류 상황의 실제 테스트가 통과했는지를 기준으로 판단합니다.

이 결정은 검증을 포기하는 것이 아니라, **개발 속도와 검증 비용 사이에서 우선순위를 조정하고, 그에 따른 위험을 마지막 통합 검증으로 보완하려는 선택**입니다.

단, 실제 프로젝트에서 사용자가 이런 판단을 했다는 원문이 확인되지 않는다면, 이 답변을 사용자의 경험인 것처럼 작성해서는 안 됩니다.

**핵심 한 문장:** 좋은 AI 협업은 검증을 무조건 많이 하는 것이 아니라, 무엇을 확인하고 어떤 위험을 감수할지 근거를 갖고 판단하는 것입니다.

## 이 예시를 사용하는 방법

답변을 생성할 때는 위 네 가지 예시의 **설명 품질**을 참고한다.

특히 다음을 지킨다.

1. 처음부터 중요한 결론을 사람이 이해할 말로 설명한다.
2. 구체적인 상황과 숫자가 있으면 실제 처리 순서를 따라간다.
3. 여러 모듈이 연결되는 기능이라면 입력부터 최종 결과까지 설명한다.
4. 선택한 방식의 이유와 포기한 목표를 함께 설명한다.
5. 실제 검증과 구현상 예상, 확인하지 못한 부분을 구분한다.
6. 사용자가 내린 선택이나 실제 AI 협업 사례는 원문 근거가 있을 때만 설명한다.

**문장 끝을 `~해요`로 바꾸는 것만으로 이 품질을 충족했다고 판단하지 않는다.**

현재 프로젝트의 코드와 요구사항을 읽지 않고 위 숫자, 기능, 결과, 기술 선택을 그대로 복사해서는 안 된다.

중요한 질문을 충분히 발굴하고, 각각의 답변을 읽었을 때 그 프로젝트를 실제로 이해할 수 있도록 작성하는 것이 목표다.
