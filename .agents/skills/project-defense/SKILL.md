# 프로젝트를 여섯 질문으로 이해하기

## 목적

사용자가 직접 작성하지 않은 코드도 **어떻게 동작하고, 왜 그렇게 만들었으며, 상황이 바뀌면 어떻게 되는지** 설명할 수 있도록 돕는다.

실제 프로젝트에서 가장 중요한 질문 **정확히 6개**를 만들고, 답변을 읽는 것만으로도 프로젝트의 핵심을 이해할 수 있는 완성형 모범답안을 작성한다.

## 실행과 자료 확인

- 사용자가 요청할 때만 실행하며, 개발 진행이나 완료 판정을 막지 않는다.
- 최신 코드, 요구사항·SPEC, 실제 검증 결과, 설계 선택, 사용자와 AI의 협업 기록을 확인한다.
- 기존 학습 문서가 있다면 참고하되 실제 코드와 대조한다.
- 기본 출력은 `docs/PROJECT_DEFENSE.md`다. `docs/`가 없으면 생성한다. 사용자가 채팅만 요청하면 파일을 만들지 않는다.
- 코드·테스트·기존 문서·제출물은 수정하지 않는다.

## 질문 6개 구성

다음 여섯 관점을 각각 하나의 핵심 질문으로 다룬다.

**Q1. 핵심 알고리즘·설계 선택**

실제 사용한 처리 방법의 결과, 선택한 이유, 현실적인 대안, 포기한 목표와 한계를 묻는다. 가능하면 구체적인 입력값을 제시한다.

**Q2. 프로젝트 전체 데이터·상태 흐름**

사용자 입력이나 자료 선택부터 검증, 핵심 계산, 저장, 최종 조회·출력까지 연결해 묻는다. 각 구성요소의 실제 책임과 상태 변화도 설명하도록 한다.

**Q3. 구현·검증·가정의 경계**

실제로 구현한 기능과 실행해 검증한 항목, 코드로만 예상한 동작, 미구현·미검증·가정을 구별하도록 한다. 다른 사람이 결과를 재현하는 방법도 묻는다.

**Q4. 실패·재시작·조건 변경**

실행 중 오류, 중단과 재시작, 입력·자료·조건 변경 등 프로젝트에서 중요한 상황을 선택한다. 진행 중인 작업과 기존 저장 결과가 각각 어떻게 되는지 묻는다.

**Q5. 규모·극단 조건·검증 설계**

현재 구현의 우선적인 성능·안전성 위험과 요구 규모 변화의 영향을 묻는다. 실제로 확인할 입력, 측정 지표, 예상 결과와 통과 기준을 제안하도록 한다.

**Q6. AI 협업과 사용자의 판단**

실제 작업 기록에서 사용자가 AI의 제안을 수용·수정·거절·보류한 사례와 판단 근거를 묻는다. AI의 맥락 누락·오류가 있었다면 대응 과정도 다룬다. 기록되지 않은 사건은 만들어내지 않는다.

### 질문과 제목의 가독성

질문도 모범답안만큼 이해하기 쉽게 작성한다.

`references/ANSWER_STYLE.md`의 질문 예시를 문체와 구성의 기준으로 삼는다.

질문 제목부터 누가 무엇을 하는 상황인지 알 수 있어야 한다. 추상적인 기술 표현을 제목으로 압축하지 않는다.

- **나쁜 예:** "9개 신청이 두 번의 지원으로 완료될 때 입력은 어떻게 결과가 되나요?"
- **좋은 예:** "Alice가 물품 9개를 신청했습니다. 관리자가 4개를 먼저 지급하고 나머지 5개를 지급하면 프로그램은 어떻게 동작하나요?"

질문과 답변을 완성한 뒤, 처음 보는 사람이 추가 설명 없이 상황을 이해할 수 있는지 확인하고 어려운 표현은 다시 작성한다.

### 출제 원칙

- **질문은 정확히 6개다.** 보너스 문항이나 별도 퀴즈를 추가하지 않는다.
- 질문 하나마다 한 가지 중심 상황을 두되, 밀접하게 연결되는 판단을 함께 묻는다.
- 프로젝트의 핵심을 관통하도록 여러 모듈·기술 선택·상태 변화를 연결한다.
- 실제 코드에서 답을 도출할 수 있는 구체적인 상황을 사용한다.
- 해당 프로젝트에 없는 기능이나 장애를 구현된 사실처럼 전제하지 않는다.
- 여섯 관점은 유지하되, 업무 사례·숫자·구현 기술·질문 표현은 프로젝트마다 새로 정한다.
- 실제 결정 기록이 없으면 확인 가능한 선택·구현 사실을 바탕으로 묻고 근거 부족을 밝힌다.

## 완성형 모범답안

**가장 중요한 기준은 답변을 읽는 것만으로 프로젝트를 이해할 수 있어야 한다는 점이다.**

반드시 `references/ANSWER_STYLE.md`를 읽고 완성형 답변의 설명 방식을 참고한다. 예시의 업무와 숫자, 구현 방식을 복사하지 않는다.

각 답변은 다음을 지킨다.

1. **결론부터 쉽게 설명한다.** 함수 이름이나 전문용어로 시작하지 않는다.
2. **실제 상황을 따라간다.** 입력 → 검증·판단 → 처리·계산 → 저장·상태 변화 → 결과를 연결한다.
3. **선택의 이유와 한계를 설명한다.** 중요한 대안과 포기한 목표도 구분한다.
4. **검증 근거를 밝힌다.** 구현, 실제 실행, 기록상 결과, 코드 기반 예상, 미검증을 혼동하지 않는다.
5. **실제 기록에 충실한다.** 사용자 판단과 AI 제안, 당시 사실과 사후 해석을 구분한다.
6. **처음 읽는 사람도 이해할 수 있게 작성한다.** 낯선 개념은 작은 예시로 풀고, 코드 위치와 기술 용어는 필요한 시점에 연결한다.

모범답안은 짧은 정답 요약이 아니라 **프로젝트를 만든 개발자가 다른 사람에게 충분히 이해시키는 완성된 설명**이어야 한다.

ChatGPT Chat 모드에서 옆 사람에게 설명하듯 자연스러운 한국어를 쓴다. 단순히 문장 끝을 `~해요`로 바꾼 기술 보고서는 허용하지 않는다.

## 출력 구성

`docs/PROJECT_DEFENSE.md`에 다음을 작성한다.

1. 프로젝트의 현재 구현 상태와 참고한 근거
2. 핵심 질문 6개의 목차
3. 각 질문의 구체적인 상황과 완성형 모범답안
4. 각 답변의 실제 코드·검증·결정 근거
5. 각 답변에서 기억할 핵심 한 문장

중요한 설명이 길어지면 모범답안을 충분히 작성하되, 질문 개수는 늘리지 않는다.

## 작성 후 품질 검토

여섯 답변을 완성한 다음 다음 항목을 확인한다.

- 실제 코드와 처리 순서·결과가 일치하는가?
- 알고리즘·전체 흐름·검증·실패·확장·AI 협업을 모두 실질적으로 다뤘는가?
- 처음 보는 사람도 입력부터 결과까지 따라갈 수 있는가?
- 중요한 기술 선택의 이유와 대가가 설명돼 있는가?
- 실제 검사와 미검증, 사용자 판단과 AI 제안을 구분했는가?
- 함수·파일 이름을 나열하거나 말투만 부드럽게 바꾼 설명은 없는가?
- 질문 제목과 본문을 처음 보는 사람이 읽어도 추가 설명 없이 상황과 질문 의도를 이해할 수 있는가? 추상적이거나 어색한 표현이 있다면 다시 작성한다.

**이해하기 어려운 답변은 사실과 질문의 의도를 유지하면서 다시 작성한다.**
