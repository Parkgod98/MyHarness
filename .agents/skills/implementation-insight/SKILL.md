# 중요한 구현 선택 이해하기

## 목적

사용자가 직접 작성하지 않은 코드도 **실제로 어떻게 구현됐는지**, **왜 그런 방법을 선택했는지**, **어떤 상황에서 결과가 달라지거나 실패하는지** 설명할 수 있도록 돕는다.

프로젝트 소개나 파일 목록을 길게 반복하는 대신, 실제 동작을 좌우하는 구현상의 선택과 그 근거에 집중한다. 특히 **현업이 정한 요구와 개발 과정에서 선택한 구현 방식**을 혼동하지 않도록 한다.

## 호출과 작업 범위

- **사용자가 이 Skill을 호출하거나 명시적으로 요청할 때만** 실행한다. 개발 도중 자동으로 긴 설명을 시작하거나 구현 진행을 막지 않는다.
- 사용자가 특정 기능이나 개발 단위를 지정하면 그 범위만 다룬다. 전체 구현을 요청하면 전체 관련 코드를 살펴본다.
- **기본 결과는 학습 문서다.** 별도 지시가 없다면 프로젝트의 `docs/IMPLEMENTATION_INSIGHTS.md`를 생성하거나 최신 코드 기준으로 갱신한다. `docs/`가 없으면 생성한다.
- 사용자가 파일명이나 저장 위치를 지정하면 그 지시를 우선한다. **"문서 없이 채팅에서만 설명해 줘"**처럼 명시하면 파일을 생성하지 않고 대화로만 답한다.
- 생성·갱신 후 대화창에는 **어디에 저장했는지, 어떤 범위를 분석했는지, 가장 중요한 발견이 무엇인지**만 간결히 알려준다. 문서 전체를 채팅에 반복하지 않는다. 사용자가 요청하면 상세히 설명한다.
- 코드 수정, 리팩터링, 새 테스트나 추가 기능 구현은 별도 요청이 없는 한 수행하지 않는다. **분석 문서 외 기존 코드와 문서는 수정하지 않는다.**

## 구현 상태와 변경분 확인

분석한 코드·자료의 범위와 확인한 구현 상태를 문서 앞에 적는다.
기존 문서를 읽은 것만으로 최신 구현을 확인했다고 하지 않는다.

변경분을 요청받으면 이전 상태와 현재 구현을 비교하고,
추가·변경·삭제된 동작과 그 영향을 받는 설명을 갱신한다.
비교할 이전 상태가 없으면 변경 이력을 추정하지 않는다.

요청하지 않은 범위를 다시 전수 분석하지 않되,
공유 규칙·인터페이스 변경으로 영향받는 부분은 함께 확인한다.
확인하지 않은 기존 항목은 최신 검토 범위와 구분한다.

## 중요한 포인트를 찾는 방법

1. 대상 코드의 실행 진입점, 주요 호출 경로, 핵심 모듈과 테스트를 실제로 확인한다. SPEC이나 과거 대화가 있으면 당시 선택 이유를 대조한다.
2. **사용자가 모르면 실행 결과, 품질, 안전성, 성능, 유지보수 또는 변경 영향을 잘못 이해할 수 있는 선택**을 찾는다.
3. 주로 알고리즘과 탐색, 데이터 표현과 상태 변경, 처리 순서와 분기, 모듈 경계와 의존성, 오류·예외와 경계 조건, 외부 인터페이스, 동시성·성능, 테스트의 검증 범위를 살핀다. 이 범주를 모두 채우려고 억지로 항목을 만들지는 않는다.
4. 사소한 문법, 자명한 이름 붙이기, 비슷한 구현을 반복 설명하는 항목은 제외하거나 묶는다. 반면 **서로 다른 중요한 결정은 빠뜨리지 않는다.**
5. **항목 개수에 상한도 하한도 두지 않는다.** 중요한 지점이 2개면 2개, 30개면 30개, 실제로 150개라면 150개를 다룬다. 길다는 이유만으로 중요한 항목을 조용히 생략하지 않는다.
6. 범위가 넓다면 먼저 기능별 **전체 포인트 목차**를 만든다. 설명이 길어지면 기능별 절로 나누어 작성한다. 한 번에 전부 확인하지 못하면 **완료한 범위와 아직 살펴보지 못한 범위**를 문서에 명시한다. 일부만 검토하고 전수 검토했다고 말하지 않는다.

## 중요도와 항목의 성격 구분

**전부 기록하되, 무엇부터 공부해야 할지 드러내기 위해** 각 항목에 다음을 표시한다.

- **우선순위:** `핵심` / `중요` / `참고`. 실행 결과를 좌우하거나, 오류·데이터 손상 위험이 크거나, 변경 영향과 검증 한계를 이해하는 데 필수라면 `핵심`으로 둔다. 포인트 개수에 맞춰 억지로 등급 비율을 정하지 않는다.
- **성격:** `업무 규칙` / `구현 선택` / `실제 동작·한계` / `결함 후보` 등 해당하는 구분. 복합적인 경우 둘 이상 표시할 수 있다.
- **결함 후보의 확인 상태:** 코드에서 추론한 **미재현 의심**인지, 테스트나 실행으로 **재현한 현상**인지 구분한다. 원인·영향·재현 여부를 단정하지 않는다.
- 업무 규칙은 원래 요구사항·현업 근거를 제시하고, 구현 선택은 실제 코드 및 확인 가능한 결정 기록에 근거해 설명한다. 현재 코드가 그렇게 작성됐다는 사실만으로 **사용자가 그 구현을 승인했거나 AI가 특정 이유로 선택했다**고 지어내지 않는다.

`참고` 등급이라고 생략하지 않는다. 중요한 포인트를 모두 수록하되, 문서 앞부분에 `핵심`부터 찾아 읽기 쉬운 길잡이를 둔다.

## 각 포인트의 설명 방식

각 항목을 짧고 자연스러운 한국어로 다음 순서에 맞춰 설명한다. 주제에 필요 없는 칸은 생략한다.

1. **구체적인 상황을 담은 질문과 결론:** 사용자가 궁금해할 상황을 질문으로 쓰고 실제 결과부터 답한다.
2. **우선순위와 성격:** 핵심·중요·참고, 업무 규칙·구현 선택·실제 동작·한계·결함 후보 중 적절한 항목을 표시한다.
3. **작동 예시:** 작은 입력·상태 변화를 따라 실제 처리와 결과를 설명한다. 미실행 예시는 코드 기반 예상이라고 표시한다.
4. **실제 구현 근거:** 관련 파일·함수·자료 위치와 핵심 구현을 연결한다. 필요한 경우에만 코드 몇 줄을 보여준다.
5. **선택 이유와 대안:** 반드시 지킬 조건과 선택한 방법을 구분하고, 실제 선택 이유와 대안·trade-off를 설명한다. 대안이 무의미하면 억지로 만들지 않는다.
6. **한계와 확인:** 연결된 검증이 확인한 것·확인하지 못한 것과 실패·변경 영향을 구분한다.
7. **핵심 한 문장:** 사용자가 무엇을 이해하고 기억하면 되는지 간단하게 마무리한다.

당시 결정 이유는 기록이 있을 때만 설명한다.
기록이 없으면 현재 구현의 장단점에 대한 사후 분석으로 구분한다.

실행하지 않은 예시는 코드 기반 예상으로 표시한다.
조건을 바꾼 예시는 단순히 "다시 테스트해야 한다"로 끝내지 말고,
어떤 분기·상태·결과가 왜 달라지는지 설명한다.

이미 설명한 배경을 매 항목에서 반복하지 않는다. 단순한 항목은 짧게, 복잡하거나 실패 위험이 큰 항목은 필요한 만큼 충분히 풀어 쓴다.

## 기본 학습 문서 구성

`docs/IMPLEMENTATION_INSIGHTS.md`를 기본 경로로 사용한다.

- 맨 앞에 **무엇을 분석했는지**와 기능별 **전체 포인트 목차**를 둔다. 목차에는 **각 항목의 우선순위, 성격, 실제 코드 위치**를 함께 표시한다.
- 그다음 **우선 읽으면 좋은 핵심 항목**을 안내한다. 핵심 요약은 길지 않게 작성하되, 나머지 중요 포인트를 삭제하지 않는다.
- 본문에서는 찾아낸 모든 중요한 항목을 빠짐없이 다루고, 실제 코드 근거와 연결한다. 긴 프로젝트는 기능별로 나눠 읽기 편하게 구성한다.
- **업무 규칙, 구현 선택, 실제 동작과 한계, 결함 후보**를 구분하고, 결함 후보는 재현 여부와 후속 검증 필요성을 명시한다.
- 실제 코드가 어떻게 동작하는지 알 수 있는 **작은 입력·상태 변화 예시**를 적절히 사용한다. 특히 예상 결과와 실제 결과를 혼동하지 않는다.
- 마지막에는 사용자 스스로 설명해 볼 질문을 적절한 만큼 제안할 수 있다. 정답 제출을 개발 완료 조건으로 삼지 않는다.
- **확인한 코드 범위, 검토하지 못한 부분, 근거가 부족한 설계 이유, 실행하지 않은 검사**를 분명히 표시한다.
- 이미 문서가 있으면 현재 요청 범위와 최신 코드에 맞게 갱신하되, 요청 밖의 다른 문서로 내용을 분산하지 않는다. 기존 SPEC, REPORT, STEP, `PROJECT_WALKTHROUGH.md`를 복제하지 않는다.

## 정확성과 말투

- **설명은 결론부터 자연스러운 한국어로 작성한다.** 구체적인 상황 → 실제 결과 → 이유 → 코드·자료·검증 근거를 연결한다. 낯선 용어는 필요한 순간에 쉬운 뜻과 함께 소개한다.
- **질문에 대한 답부터 사람 말로 알려준다.** '`Database.connection`은 ...'처럼 함수명·기술 용어로 문단을 열지 말고, '두 사람이 동시에 예약하면 어떻게 될까요? 이 프로그램에서는 먼저 처리한 사람만 성공해요. 왜냐하면...'처럼 구체적인 상황 → 실제 결과 → 이유를 자연스러운 해요체로 풀어준다. 코드 위치와 정확한 명령은 그다음에 연결한다.
- '~을 수행한다', '~에 근거한다', '~를 보장한다' 같은 딱딱한 보고서 문장을 반복하지 않는다. '~해요', '~되는 거예요', '~때문이에요'처럼 설명하되 과장·가벼운 농담·장황한 비유는 피한다. 기술적 정확성과 검증·미검증의 구분은 그대로 지킨다.
- **나쁜 설명:** '`Database.connection(write=True)`는 `BEGIN IMMEDIATE`를 실행해 쓰기 작업을 직렬화한다.'
- **좋은 설명:** '두 사람이 같은 방을 동시에 예약하면 어떻게 될까요? 둘 다 빈방이라고 생각한 채 저장하면 곤란하겠죠. 그래서 이 프로그램은 빈방인지 확인하기 **전에** 먼저 처리 순서를 잡아요. 앞사람이 예약한 뒤 뒷사람이 다시 확인하니까 같은 시간을 두 번 예약하지 않게 되는 거예요. 이때 사용하는 명령이 `BEGIN IMMEDIATE`예요.'

문체만 수정하는 요청에서는 사실과 구성을 보존한다.
구현 변경을 반영하는 요청에서는 실제 코드에 맞춰
항목·예시·검증 근거를 추가·수정·삭제한다.

설명을 짧게 만들기 위해 중요한 포인트를 삭제하지 않는다.
반대로 더 이상 존재하지 않는 동작을 항목 수 보존을 위해 남기지 않는다.

- 최신 **실제 코드**를 근거로 한다. 계획만 있고 구현되지 않은 기능은 구분한다.
- 대화 기록이 없는 결정을 '당시 이렇게 판단했다'고 지어내지 않는다.
- 테스트를 실제로 실행하지 않았다면 통과했다고 쓰지 않는다. 이미 있는 로그를 인용할 때에도 그 출처와 범위를 분명히 한다.
- 코드가 보장하는 결과와 가능성·추정을 구분한다. 실수하기 쉬운 계산과 경계는 구체적으로 확인한다.
- **결론부터, 일상적인 한국어로** 설명한다. 낯선 개념은 짧은 비유나 작은 예시로 풀어주고, 긴 보고서식 서술이나 파일명 나열을 피한다.
- 사용자가 질문하면 이해되지 않은 지점만 더 깊게 설명한다. 확인 질문으로 개발 진행을 막지 않는다.

`project-walkthrough`는 프로젝트 전체를 이해하는 도구이고, 이 Skill은 **중요한 구현 선택을 실제 코드 기준으로 이해하는 도구**다.
