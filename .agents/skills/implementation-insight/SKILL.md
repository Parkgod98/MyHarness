# 중요한 구현 선택을 이해하기

사용자가 요청할 때만 실행한다. 목적은 **AI가 작성한 코드라도 사용자가 실제 동작과 선택 이유를 자기 말로 설명할 수 있게 하는 것**이다. 전수 감사 보고서를 길게 작성하는 것이 목표가 아니다.

## 읽을 자료와 작업 범위

- 현재 코드·호출 경로·중요 테스트와 SPEC·업무 규칙·결정 기록을 확인한다. 과거 문서가 아닌 현재 구현을 기준으로 설명한다.
- 별도 지정이 없다면 \`docs/IMPLEMENTATION_INSIGHTS.md\` 하나만 생성·갱신한다. 사용자가 채팅 설명만 원하면 파일을 만들지 않는다.
- 기존 코드, SPEC, REPORT, 제출물과 다른 학습 문서는 수정하지 않는다. 학습 목적만으로 테스트·빌드·리팩터링을 추가 수행하지 않는다. 새 검증이 필요하면 별도 요청으로 구분한다.

## 무엇을 찾아야 하나

1. **사용자가 모르면 결과를 잘못 설명할 핵심 선택**을 찾는다. 예: 알고리즘과 우선순위, 숫자·시간 계산, 입력 검증, 권한, 저장 순서와 상태 변경, 중복·동시 요청, 실패 복구, 규모의 한계.
2. 사소한 함수나 비슷한 현상은 하나의 원리로 **묶어서** 설명한다. 개수가 많다는 이유로 서로 다른 중요한 결정이나 실제 위험을 조용히 누락하지 않는다.
3. 중요도를 \`핵심 / 중요 / 참고\`로 나눈다. **핵심은 먼저 꼭 이해해야 할 내용만 엄선**한다. 항목 수나 등급 비율을 억지로 맞추지 않는다. 실제로 중요한 포인트가 많으면 주제별로 묶고 읽는 순서를 알려준다.
4. \`업무가 정한 규칙\`, \`사용자가 선택한 것\`, \`AI 또는 코드의 구현 선택\`, \`실제 동작과 한계\`, \`결함 후보\`를 혼동하지 않는다. 선택 이유는 대화·기록에 없으면 당시 의도를 추측하지 않는다.
5. 결함 후보는 **실제 재현 / 코드상 의심(미재현)**을 표시한다. 미재현 위험을 확정 장애로 쓰지 않되, 심각한 위험을 설명에서 숨기지도 않는다.

## 학습 문서의 읽는 순서

- **① 가장 먼저 읽을 핵심:** 처음 5~10분에 볼 내용. 프로젝트에서 결과를 좌우하는 구현 원리들을 쉬운 질문과 한두 문장으로 안내한다. 기능별 목록을 길게 펼쳐 놓고 시작하지 않는다.
- **② 중요한 원리를 이해하기:** 서로 연결되는 결정을 묶어 자세히 가르친다. 각 원리에 대해 **상황 → 실제 처리 → 선택 이유·대안 → 코드 근거 → 확인한 것·못 한 것** 순서로 설명한다. 실제 수치나 작은 입력을 사용하되, 미실행 계산은 예상이라고 표시한다.
- **③ 나머지 구현 포인트:** 빠뜨리면 안 되는 다른 결정·한계·검증은 기능별로 간결하게 기록한다. 쉬운 내용까지 모두 같은 길이의 일곱 항목짜리 설명으로 늘리지 않는다. 필요하면 짧은 표와 코드 위치를 쓴다.
- **④ 실제 검증과 남은 위험:** 중요 결과의 입력·기대·관측, 실행 주체와 시점, 미검증·미재현 위험을 요약한다. 상세 로그·줄 번호는 본문마다 길게 반복하지 않고 근거 위치로 연결한다.

동일한 사실을 앞의 목차·핵심 요약·본문·마지막 기억할 점에 반복하지 않는다. \`project-walkthrough\`의 서비스 소개도 복제하지 않는다. 내용의 깊이는 중요도와 이해 난도에 맞추고 **처음부터 끝까지 한 번에 읽어야만 핵심을 알 수 있는 문서**를 만들지 않는다.

## 핵심 원리를 한 단계 더 이해하는 방법

실제 코드와 검증 기록을 바탕으로, **결과를 좌우하거나 잘못 이해하기 쉬운 핵심 원리**에만 다음 관점을 필요한 만큼 덧붙인다.

- **선택의 대가:** 현재 방식으로 얻은 것뿐 아니라 현실적인 대안과 비교해 무엇을 포기했는지 설명한다. 당시 의도의 증거가 없다면 현재 구현의 장단점으로만 설명한다.
- **조건 변화:** 중요한 입력·상태·규모·요구·실행 환경 하나가 달라지거나 처리 도중 실패하면 어떤 결과가 나오는지 작은 상황으로 따라간다. 진행 중인 작업과 이미 저장된 결과를 구분하고, 구현하지 않은 복구를 있다고 말하지 않는다.
- **검증의 다음 단계:** 실제 입력·실행·관측으로 확인한 것과 아직 보장하지 못한 것을 구분한다. 중요한 미검증 위험이라면 다른 사람이 재현할 수 있도록 어떤 입력을 준비해 무엇을 실행하고 어떤 결과·지표를 비교할지 간단히 제안한다. 제안한 테스트를 실행한 것으로 표현하지 않는다.

**이 관점들은 모든 구현 포인트에 붙이는 필수 출력 양식이 아니다.** 핵심 선택 몇 개에만 선택적으로 녹여 쓰고, 관련된 원리는 함께 설명한다. 사소한 구현에는 대안·가상 실패·추가 실험을 억지로 만들지 않는다. 다섯 개 소제목을 반복해 문서를 길게 만드는 일은 금지한다.

## 설명하는 말투 — 특히 중요

- 코드보다 **사람이 겪는 상황부터** 설명한다. '트랜잭션·멱등성·WAL·p95' 같은 용어로 시작하지 말고, 왜 필요한지 보여준 다음 용어와 실제 코드를 연결한다.
- 기술적 사실을 단순화하되 틀리게 바꾸지 않는다. 결정의 장점뿐 아니라 포기한 것, 실패 시 결과, 검증 한계도 쉬운 말로 설명한다.
- 문장은 대화하듯 짧고 자연스럽게. 추상 명사 연속, 슬래시로 나열한 개념, 파일명·함수명 줄줄이 나열, 보고서식 면책 문장을 피한다. 실제 코드·근거 표시는 짧게 덧붙인다.
- **나쁜 예:** "\`Database.connection(write=True)\`는 \`BEGIN IMMEDIATE\`를 수행하여 동시 쓰기의 직렬화와 무결성을 보장한다."
- **좋은 예(결론 → 실제 동작 → 이유와 대안 → 검증과 한계 → 조건 변화를 자연스럽게 연결한 문체):**
  > **두 사람이 같은 방을 동시에 예약하면 어떻게 될까?** 먼저 예약을 확정한 한 사람만 성공해야 해. 같은 시간에 두 예약이 생기면 안 되니까.
  >
  > Alice와 Bob이 동시에 예약을 누른다고 해보자. 이 예시의 프로그램은 빈자리를 확인하기 **전에** DB 쓰기 순서를 확보해. Alice가 먼저 저장했다면 Bob은 그 결과를 확인하고 이미 예약된 시간을 알아채지.
  >
  > 왜 이렇게 만들었을까? 빈자리를 확인하고 나중에 따로 저장하면 두 사람 모두 방이 비었다고 판단할 수 있기 때문이야. 다른 잠금 방식도 가능하지만 이 예시에서는 SQLite의 \`BEGIN IMMEDIATE\`를 사용해. 대신 쓰기 요청이 몰리면 대기 시간이 길어질 수 있지.
  >
  > 만약 실제 검사에서 서로 다른 요청 8개 중 하나만 성공한 기록이 있다면, 그 검사에서 중복 예약을 막았다고 말할 수 있어. **그렇다고 100명이 동시에 요청해도 같은 속도로 처리된다는 뜻은 아니야.** 동시 요청 수를 늘려 중복 예약 여부, 잠금 실패율, 응답 시간을 비교해야 확인할 수 있어.
  >
  > **근거:** 현재 코드에서 쓰기 순서를 확보하는 부분과 실제 실행한 검사 기록을 짧게 연결한다. 검사를 수행하지 않았다면 '코드상 예상, 동시 요청은 미검증'이라고 적는다.
- 위 예시는 특정 프로젝트용 정답이나 필수 기술 스택이 아니다. 반드시 **현재 코드에 맞는 다른 실제 상황**을 선택한다. 실험하지 않은 수치·실패 사례·결정 이유는 만들어내지 않는다. 다섯 관점은 좋은 설명을 생각하는 기준일 뿐 모든 원리에 강제할 소제목·체크리스트가 아니다.

## 마무리와 보고

- 프로젝트·코드의 어떤 범위를 읽었는지, 확인하지 못한 범위와 중요한 결함 후보를 구분한다. 실제 테스트를 새로 돌리지 않았다면 그렇게 적는다.
- 스스로 설명해 볼 질문은 정말 중요한 것만 제시한다. 질문의 답을 개발 완료 승인 조건으로 삼지 않는다.
- 결과를 저장한 위치와 우선 읽어야 할 내용을 대화에서 짧게 알려준다. 사용자가 더 깊게 묻는 부분만 상세히 설명한다.
